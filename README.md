# kpi-report — Claude Code Skill для Omnidesk

Считает KPI-отчёт поддержки по одному сотруднику за произвольный период:
скорость ответов (медианы), SLA первого ответа с делением на лёгкие/критичные
нарушения, аудит критичных случаев по changelog (личное или унаследованное),
командную метрику «без ответственного». Два уровня отчёта — `personal` (что
видит сотрудник) и `manager` (полная картина с аудиторским следом).

Вся детерминированная арифметика и работа с Omnidesk API — в Python-хелперах
(`scripts/`). Роль Claude (через Claude Code Skill в `.claude/skills/kpi-report/`) —
распарсить запрос на естественном языке, руками досмотреть спорные пограничные
случаи (то, что автоматика размечает грубо) и напечатать готовый отчёт в чат.

## Установка

### 1. Python
```
python --version
```
Нужен Python 3.9+. Если команда не найдена — поставьте с
https://www.python.org/downloads/, отметив «Add Python to PATH».
Зависимостей кроме стандартной библиотеки нет.

### 2. Claude Code
Установите [Claude Code](https://claude.com/claude-code) и войдите в свой
аккаунт Anthropic.

### 3. Склонируйте репозиторий
```
git clone <URL этого репозитория>
cd kpi-report-skill
```

### 4. Настройте доступ к Omnidesk
Скопируйте `.env.example` в `.env` и впишите свои значения:
```
cp .env.example .env
```
```
OMNIDESK_API="ваш API-токен"      # Настройки -> Программисту -> API-ключ
EMAIL="ваша_почта@example.com"    # логин агента в Omnidesk
SUBDOMAIN="ваш-поддомен"          # из https://<SUBDOMAIN>.omnidesk.ru
```
`.env` не должен попадать в git — он уже в `.gitignore`.

### 5. Откройте проект в Claude Code
Запустите Claude Code в папке `kpi-report-skill`. Скилл подхватится
автоматически из `.claude/skills/kpi-report/`.

### 6. Заведите список своих операторов
Откройте `.claude/skills/kpi-report/SKILL.md` и впишите реальных сотрудников
(имя → staff_id) в раздел «Разбери запрос» — это позволит Claude узнавать имена
без уточняющих вопросов на каждый запрос.

## Использование

Просто пишите в чат обычными словами, например:
> сделай отчёт по Ивану за прошлую неделю

> отчёт руководителю по Марии с 1 по 15 июля

> покажи личный отчёт по Ивану за вчера

Claude сам разберёт период и сотрудника, запустит хелпер, досмотрит спорные
критичные случаи и напечатает отчёт. Если период или сотрудник не указаны
однозначно — переспросит, а не будет угадывать (от периода зависят деньги).

Первый прогон за новый период обращается к Omnidesk API и может занять
несколько минут (rate limit). Повторный прогон за тот же период — мгновенно,
берётся из локального дискового кэша (`scripts/cache/`, не входит в репозиторий
и не должен коммититься — там реальная переписка с клиентами).

## Прямой запуск хелпера (без Claude)

```
python scripts/report.py --staff "Имя Сотрудника" --from "2026-07-12 00:00:00" --to "2026-07-18 23:59:59" --view manager
```

Флаги:
- `--view manager|personal` — уровень отчёта (по умолчанию `manager`)
- `--json` — сырой JSON вместо готового рендера (для программной обработки)
- `--cache` — читать/писать ответы API в `scripts/cache/` (рекомендуется при
  повторных прогонах за один и тот же период)
- `--html <path>` — дополнительно сохранить отчёт отдельной HTML-страницей

## Структура проекта

```
scripts/
  omni_client.py      — тонкий клиент Omnidesk API (пагинация, троттлинг, кэш)
  sla_violations.py   — классификация нарушений SLA первого ответа
  audit_critical.py   — аудит критичных случаев по changelog (личное/унаследованное)
  no_responsible.py   — командная очередь «без ответственного», «забытые в работе»
  calibration.py      — калибровочная грация для молодых направлений
  load_baseline.py    — скользящая база нагрузки, сравнение потока с обычным
  report.py           — оркестратор: собирает всё в готовый отчёт
  report_html.py       — опциональный HTML-рендер отчёта
.claude/skills/kpi-report/
  SKILL.md             — инструкция для Claude Code Skill
  evals/evals.json     — тестовые сценарии для проверки скилла
```

## Дополнительные инструменты

### Калибровочная грация (`calibration.py`)
Когда запускается новое направление, первые недели метрики по нему объективно
хуже: нет шаблонов, база знаний пустая, поток непредсказуем. Хелпер помечает
такие направления, чтобы их нарушения были видны отдельной строкой и не читались
как провал оператора.

```
python scripts/calibration.py --cache
```

Возраст направления берётся из `groups.json` (`created_at`), поэтому новая
группа подхватывается **автоматически** — вести список руками не нужно. Если
нужно переопределить (направление формально новое, но это переезд старого
потока — или наоборот), скопируйте `scripts/calibration.example.json` в
`scripts/calibration.json` и опишите исключения. Без этого файла всё работает
на настройках по умолчанию: окно 4 недели, авто-детект включён.

Грация **ничего не вычитает** из метрик — только помечает. Решение остаётся за
руководителем; правила «норматив соблюдён/не соблюдён» в проекте сознательно нет.

### Скользящая база нагрузки (`load_baseline.py`)
Отвечает на вопрос «поток в этот период был обычный или выше обычного»:

```
python scripts/load_baseline.py --from "2026-07-12 00:00:00" --to "2026-07-18 23:59:59" --weeks 4 --cache
```

Считает средний поток по дню недели и часу за N недель и сравнивает с фактом,
показывает часы всплесков и нагрузку на оператора в рабочее окно.

⚠️ **Если поток у вас растёт**, плоское среднее за 4 недели систематически
занижено, и любой период будет выглядеть «выше обычного». Хелпер это замечает,
печатает предупреждение и рядом даёт более честное сравнение — с последней
неделей базы. На растущем потоке ориентируйтесь на вторую цифру.

## Методология

Источник истины по логике метрик и решениям по методологии — внутренняя
документация вашей команды (заведите свою, здесь её сознательно нет — это
инструмент, а не чужая бизнес-логика). Ключевые принципы, зашитые в код:

- Два уровня видимости (`personal`/`manager`) — фиксированное архитектурное
  решение, не опция.
- Считаются только метрики, без правила «норматив соблюдён/не соблюдён» —
  композитный KPI-рейтинг тут сознательно не вводится.
- Отчёт строится по запросу (сотрудник + период), не по расписанию — никогда
  не заворачивайте это в cron/scheduled task.
- Скорость (медианы) берётся нативно из лидерборда Omnidesk; аудированный SLA
  считается по changelog. Медиана, а не среднее — устойчива к выбросам.
- Пороги SLA (15 мин — норма, >20 мин — критично) заданы константами в
  `scripts/sla_violations.py` — поменяйте под свой SLA при необходимости.
