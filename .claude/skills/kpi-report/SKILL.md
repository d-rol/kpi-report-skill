# KPI-отчёт поддержки (по одному сотруднику, по запросу)

Тонкая обёртка над готовым Python-хелпером `report.py`. Скрипт делает всю
детерминированную арифметику и работу с Omni API; твоя роль — распарсить запрос,
**досмотреть спорные критичные случаи глазами** (то, ради чего скилл, а не крон)
и напечатать отчёт в чат по-русски.

## Что важно помнить (методология, не переизобретать)

Источник истины по логике метрик — `Предложение_по_KPI_поддержки.docx`
и `HANDOFF.md` в корне проекта. Ключевое:

- **Два уровня видимости — это зафиксированное требование, не опция.**
  `personal` — что видит сотрудник (скорость + реальный SLA без унаследованных
  задержек + «разобрал зависшее» справочно). `manager` — всё то же плюс сырой
  SLA Омнидеска для контраста, разбор критичных до/после аудита и командная
  метрика «без ответственного». **По умолчанию — `manager`.**
- **Считаем только метрики, без правила «норматив соблюдён/не соблюдён».**
  Композитный KPI-рейтинг пока не вводим (решение Димы 2026-07-19).
- **Не по расписанию.** Никогда не заворачивай это в cron/scheduled-task —
  период и сотрудник всегда приходят из запроса.
- Скорость (медианы) берётся нативно из лидерборда Омнидеска; аудированный SLA —
  из нашей логики по changelog. Медиана, а не среднее — устойчива к выбросам.

## Шаги

### 1. Разбери запрос
Нужны **сотрудник** (имя или staff_id) и **период** (`--from`/`--to` в формате
`YYYY-MM-DD HH:MM:SS`, МСК).
- Если период задан словами («за прошлую неделю», «с 12 по 18 июля») — переведи
  в конкретные даты. Сегодняшнюю дату бери из контекста сессии.
- Если сотрудник или период неоднозначны — **спроси**, не угадывай (от периода
  зависят деньги). Заведите здесь список своих операторов (имя → staff_id) —
  например: Иван (10001), Мария (10002); ботов/системные учётки (например,
  автоответчик) стоит пометить отдельно — по ним отчёт обычно не нужен.
- Вид: `manager` по умолчанию; `personal`, если явно просят «личный отчёт» /
  «то, что видит сотрудник».

### 2. Запусти хелпер (в JSON, чтобы досмотреть спорное)
Пути — от корня проекта `kpi_automation` (там, где открыт Claude Code). Если
оболочка не в корне — подставь префикс сам.
```
python scripts/report.py --staff "<имя|id>" --from "<...>" --to "<...>" --view <manager|personal> --json --cache
```
`--cache` обязателен при фиксированном периоде — экономит rate-limited API на
повторных прогонах. **Не запускай два таких процесса параллельно** — они делят
общий лимit 20 запросов/мин и словят 429. Один прогон за раз.

### 3. Досмотри спорные критичные случаи (это и есть работа скилла)
Хелпер размечает каждое критичное нарушение как `personal` (личное) или
унаследованное (`systemic_noresp` / `from_other`) по правилу: удержание
(reply − **самое раннее** назначение ответственного, включая авто-подхват чата
`fixed_chat`) ≤ 15 мин ⇒ унаследовано. Удержание считается в **рабочих минутах
10:00–22:00 МСК** (та же база, что нативный SLA Омнидеска — ночь между вечерним
назначением и утренним ответом не набегает). Правило грубое и на границе ошибается.
Пройди по `personal_critical_cases` и `inherited_critical_cases` из JSON и
перепроверь **только пограничные**, где правило могло промахнуться:

- **`held_min` близко к 15** (примерно 10–20 мин) — по обе стороны границы.
- **`reason` = «нет reply_staff»** — аномалия, помечена личной автоматически.
- **Авто-роутинг чата на оператора** (`fixed_chat` 0→staff в начале, потом
  оператор держал 15–35 мин): формально личное, но если чат упал в момент
  параллельной загрузки — это «завалили», а не «владел и тянул». Пограничная
  политика; помечай и выноси на решение.
- **Перештамп ответственного в момент ответа.** Омнидеск переставляет
  ответственного (`fixed_chat` или `staff`) за 1–2 сек до `reply_staff`. Хелпер
  считает удержание по **финальному непрерывному блоку владения отвечающего**
  (`answerer_ownership`): перештампы на того же оператора схлопываются (владелец
  не меняется), поэтому реальное личное удержание (оператор владел часами) не
  схлопывается в ~0. При ручной проверке смотри, когда оператор реально стал
  владельцем в своём последнем блоке, а не на секундный перештамп перед ответом.
- **Передача владения между операторами.** Если один держал обращение долго, а
  ответил другой (стал владельцем перед ответом), удержание считается только по
  блоку ОТВЕТИВШЕГО — то, что держал предыдущий, ему не в вину (`kind` станет
  `from_other`, поле `neglected_by` = staff_id того, кто держал/забыл). Так вина
  за чужой висяк не падает на того, кто разгрёб. Долгий висяк предыдущего владельца
  виден отдельно в секции «Забытые в работе».

Для такого случая подними таймлайн и реши сам:
```
python -c "import sys; sys.path.insert(0,'scripts'); from omni_client import OmniClient; import json; c=OmniClient(cache=True); print(json.dumps(c.get('cases/<CASE_ID>/changelog.json'),ensure_ascii=False,indent=2))"
```
и при необходимости `cases/<CASE_ID>/messages.json` (первый `reply_staff` = реальный
ответ). Смотри: когда оператор реально стал владельцем и сколько держал до ответа.
Если видишь, что взял из общей очереди и ответил сразу — это «разобрал зависшее»,
не в вину; если владел и тянул — личное. **Большинство случаев править не нужно**
— трогай только те, где автоматика на границе. Отметь в отчёте, если поправил
вердикт, и коротко почему.

### 4. Напечатай отчёт в чат
Чат рендерит **CommonMark в моноширинном шрифте** — HTML/CSS-виджеты тут не
рисуются, поэтому наглядность даём тем, что моноширинный markdown умеет хорошо:
Unicode-полосы (`bar()`), выровненные таблицы, markdown-ссылки на обращения.
Готовый рендер хелпера (`report.py` без `--json`, нужный `--view`) уже собран
в этом стиле — возьми его как основу и внеси правки после ручного досмотра, либо
собери сам из JSON. Держи структуру:

- **personal (кратко):** скорость (медианы) → реальный SLA одной полосой + % и
  разбивка лёгкие/критичные → «разобрал зависшее» (справочно). Без ссылок на
  обращения и менеджерского слоя.
- **manager (подробно):** скорость → две полосы «сырой Омнидеск → реально по вине»
  (наглядный контраст %) + разбивка лёгкие/критичные → строка **нагрузки**
  (`load` из JSON: поток был обычный или выше обычного) → таблица **личных
  критичных** (со ссылками) → отдельная таблица **«Требует вашей оценки — пограничные»**
  (borderline из JSON: авто-чаты, held ≈ 15–45 мин; со ссылками — руководитель
  смотрит сам или спрашивает сотрудника) → унаследованные свёрнуто (`<details>`) →
  **«Забытые в работе»** (`forgotten_in_work` из JSON: взятые обращения без
  первого ответа дольше 24 ч — живой список по сотруднику, со ссылками) →
  командная очередь «без ответственного».

Нагрузка (`load`) есть только в `manager`. Если `available: false` — напиши
причину из `reason`, а не молчи: молчание прочитается как «поток был обычный».
Случаи с `spike_ratio` пришли в час всплеска — пометь это рядом со случаем, но
вердикт из-за всплеска НЕ меняй: это контекст для руководителя, а не смягчение.

Пограничные (`"borderline": true`) НЕ суди сам в отчёте — выноси списком со
ссылками на ручную оценку руководителя (это его решение, оно money-adjacent).
Ссылки на обращения — `case_url_tpl` из JSON (`.../staff/cases/edit/<case_id>`).
Не показывай сотруднику менеджерский слой и не выдумывай правило pass/fail.

Опционально: `report.py ... --html <path>` пишет ту же информацию отдельной
красивой HTML-страницей (тема через CSS-переменные) — только если пользователь
явно просит файл, чтобы распечатать/переслать. По умолчанию — рендер в чат.

## Мини-пример
Запрос: «сделай отчёт по Ивану за прошлую неделю».
→ период 2026-07-12 00:00:00 — 2026-07-18 23:59:59, staff Иван, view manager.
→ `report.py ... --json --cache`, досмотр пограничных критичных, печать
менеджерского отчёта (цифры — иллюстративные, у вас будут свои).
